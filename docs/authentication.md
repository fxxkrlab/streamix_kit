# Authentication

`POST /sxapi/v1/sessions` accepts exactly `username` and `password`, and returns a Bearer `access_token` with the current user. Since server 0.9.0-rc.27 it also returns `expires_at` (the access token expires 24 hours later by default) and a rotating refresh token, described below. The SDK keeps the tokens in memory and omits them from Debug and error output. An application needing persistent sign-in should use its platform's protected credential store, not a plain preferences file, crash report or URL.

`DELETE /sxapi/v1/sessions/current` revokes the token used on that request. Playback sessions must be ended separately as part of normal cleanup. Revoking the login also fences its children; it is not a substitute for reporting accurate progress.

`POST /sxapi/v1/sessions/refresh` takes one of two refresh secrets in its JSON `refresh_token`, never as Bearer, and returns a new login:

- A **personal credential secret** (`stx_sxrt_`), created separately by the user, returns a child login (`OwnCredentialRefreshed`) and is not rotated. This candidate SDK supports the exchange but does not create or manage personal credentials.
- A **login refresh token** (`stx_sxls_`, server 0.9.0-rc.27 and later, `features.session_refresh`) comes with a password login: `POST /sessions` returns it as `refresh_token`, shown once, with `refresh_expires_at` (30 days unless used first, renewed by each refresh, never more than 365 days after the password login). Both are null together on a server that does not offer refresh. A refresh spends the token and returns `SessionRefreshed`: a new 24-hour `access_token` with `expires_at` and `login_id`, plus the next `refresh_token` of the chain and its `refresh_expires_at`.

Refresh one request at a time and store the new refresh token before using the new access token. A spent token presented again within 60 seconds while its successor is unused is answered again, for a response that was lost; any other reuse revokes the whole chain and every login it minted. The token is 401 when unknown, expired or revoked (logout or the end of any login of its chain), when the account is disabled, and after a password change or the end of all sessions; then ask for the password again. Use the login's `expires_at` to refresh shortly before the access token expires rather than after a 401.

In the SDK, `AuthenticatedClient::expires_at` and `AuthenticatedClient::renewal` give the login's expiry and its `LoginRenewal` (the token and `refresh_expires_at`). `Client::refresh` takes either secret, rejects a malformed one before any request, requires `features.session_refresh` for a login token and checks that the answer has the shape of the secret sent. It returns a `RefreshedLogin` whose `renewal` holds the next token before anything has used the new access token; store it, then call `activate`, which reads `/users/me` and returns the `AuthenticatedClient`. `Secret::expose_secret` exists only to move a token into protected storage.

On 401 stop using the failed credential and request sign-in. Do not repeatedly retry with the same secret. On 403 keep authentication separate from policy denial; changing a transport flag must not bypass current library, adult-content, concurrency or quota restrictions. A 503 is an infrastructure failure and must not be shown as a wrong password.

Video tickets authorize only their bound video stream. Subtitle tickets require the original Bearer **and** the subtitle header. A video credential is never accepted as general API authentication. See [credential headers](credentials-in-headers.md).
