# Browsing and paging

Read `/sxapi/v1/libraries` for the current user's visible libraries. Then query `/media` with a selected library and a bounded `limit` (maximum 100, default 30 in the current contract). Catalog data is not sent as a single full-library response. Load a small initial page, then fetch more when the user scrolls.

Preserve an opaque `next_cursor` unchanged and keep the filters and sort consistent across pages. A cursor is not a credential, does not grant access and is bound to the original login. Restart from the first page after a new login, changed filters, cursor rejection or authorization change. Counts are observations and may change between requests.

For films use `/media/{id}/versions`; for series use the series/season/episode operations in the [synchronized client specification](../spec/README.md), then select versions for the chosen episode. A media ID, episode ID and version ID are distinct. Do not align episodes by title text or manufacture file-backed episodes from metadata-only entries.

With `features.media_best_version` (server 0.9.0-rc.17 and later), every `Media` carries `version_count` and `best_version`: the picture facts (`resolution`, `width`, `height`, `hdr_type`, `bitrate_bps`, `dolby_vision_profile`) of the same version that `/media/{id}/versions` lists first. Use them to show a quality badge on list and search pages instead of one version request per work. Each fact is null until the current file is measured, and `best_version` is null when the work has no current main version. Pick the version to play from `/media/{id}/versions` as before.

With `features.version_display` (server 0.9.0-rc.24 and later), every `Version` and `BestVersion` carries `display`, which is required and may be null. For a version the server records as adult origin it is a short name the server builds from the code in the file name (normalized, for example `ABCD-123`), its tags and the technical difference that tells it apart from the other versions of the same work and episode; without a code it falls back to a short title taken from the file name, then the technical facts, then `版本 N` (version N). It is never the whole file name. Show `display.text` as the version name as it is, in the version picker, on the playback screen and wherever a version is named: it is already unique among the versions of the work and episode and fits 40 characters and 40 columns (an East Asian character counts two), so do not append your own resolution or codec label to it. `basis` says what the name came from (`code`, `title`, `technical` or `ordinal`); `code` and `family` are set only when `basis` is `code`; `tags` lists the machine names of the tags shown in `text`, in display order (`zh_sub`, `en_sub`, `uncensored`, `leak`, `decensor`, `ai_decensor`, `vr`, `3d`, `8k`, `4k`, `fps<N>`, `hdr`, `dv`, `cd<N>`, `part_upper`, `part_lower`), for icons or filters; `rules_version` names the server's rules file (`YYYY.MM.patch`). For an ordinary version `display` is null: build the label from the version facts as before.

Adult works also list their versions in the adult order instead of the quality order: Chinese subtitles first, then leak, uncensored, decensored and AI decensored in that order, then resolution, then bitrate (the weights live in the server's versioned rules file). The parts of one variant (`CD1`, `CD2`, ...) stay together in part order, and an episode group keeps the place of its first entry. Pages of an adult work are cut from that order, so keep passing `next_cursor` as usual; a work with more than 2000 versions keeps the quality order. `best_version` is the first version of that order and its `display` is that version's name, so a list or search page shows the same name the version picker shows first. A server without the capability (0.9.0-rc.23 and earlier) sends no `display` and keeps the quality order. `BestVersion` allows no other members, so a client that strictly validates responses against an older specification rejects these; validate against the synchronized specification and accept a missing `display` from an older server.

With `features.media_studio_filters` (server 0.9.0-rc.18 and later), `/media`, `/media/initials` and `/media/ids` accept `studios` (production company or network names, comma-separated, whole names ignoring case) and `studio_ids` (TMDB numbers, comma-separated), each up to 20 values. A series' networks count as its studios, so a streaming-platform row is one request: send every spelling of the platform in `studios`, or its keys from `/media/facets/studios` in `studio_ids`. Values within a parameter are alternatives; the parameters combine with every other filter and sort. Use `studio_ids` for a name that contains a comma on a server before 0.9.0-rc.19; since 0.9.0-rc.19 a comma inside a `studios` name is written `\,` and a backslash `\\` (any other backslash is literal).

With `features.media_studio_counts` (server 0.9.0-rc.19 and later), `POST /media/studio-counts` returns the counts of every row in one request, so a page can hide the empty rows before opening any of them. Send each platform's spellings as one entry of `groups` (for example `{"id": "iqiyi", "names": ["爱奇艺", "iQiyi", "iQIYI"]}`; a work counts once per group) or single names in `names`, with the same `library_id` and `media_type` the rows will use. Each count equals the total of the matching `GET /media?studios=...` request; open a row with that request. Without the capability, ask each row with `GET /media?studios=<names>&limit=1`.

With `features.media_facet_cache` (server 0.9.0-rc.20 and later), a `/media/facets/{kind}` answer may be up to `limits.media_facet_max_age_seconds` (600) seconds old; `observed_at` tells when the served answer was computed. Permission changes apply at once, while new or removed files and metadata may take that long to change the facet counts. Fetch facets when a filter panel opens and reuse them while it stays open; do not fetch them again for every grid page.

With `features.person_lookup_by_external_id` and `features.media_lookup_batch` (server 0.9.0-rc.22 and later), a page that lists people or works by TMDB or IMDb ID (a chart, a filmography) marks and opens the ones this server has without one request per entry. `GET /persons?external_ids=tmdb:31,imdb:nm0000158` takes 1 to `limits.person_external_ids_max` (50) person IDs (`tmdb:<number>` or `imdb:nm<digits>`), with at most `library_id` beside it; each returned person carries `media_count`, `movie_count` and `series_count` (the visible works crediting them, the same count as the `total` of `GET /persons/{id}/media`) and `matched` (the requested items that named them, as sent). People without a work the account can see are left out, so a missing row means nothing of theirs is available here. `POST /media/lookup` with `{"ids": ["tmdb:movie:603", "tmdb:tv:1399", "imdb:tt0133093"]}` takes 1 to `limits.media_lookup_ids_max` (500) IDs and returns one `{id, media_id, media_type, version_count}` row per ID and visible work, only for matches; open a work with `GET /media/{media_id}`. Use the typed `tmdb:movie:<n>` or `tmdb:tv:<n>` form when the type is known: an untyped `tmdb:<n>` returns both the movie and the series with that number. Since the same server version, `/media/ids` rows and `/persons/{id}/media` entries carry the work's `external_ids`, so an incremental sync maps TMDB, IMDb and TVDB IDs to works directly. Without `media_lookup_batch`, fall back to `GET /media?external_ids=` with at most `limits.media_external_ids_max` (50) IDs per request; a server without `person_lookup_by_external_id` (0.9.0-rc.21 and earlier) has no lookup of persons by ID.

Authenticated JSON reads that declare an `ETag` (63 in the player subset) take it back in `If-None-Match`; an unchanged response is a 304 without a body. The tag is per account; send it back exactly as received (a `W/` prefix added by edge compression still matches). Since server 0.9.0-rc.21 the tag of a JSON object with a top-level `observed_at` (the read time) ignores that member, so personal lists such as `/users/me/resume`, `/users/me/next-up` and `/users/me/favorites`, and facet pages, revalidate with 304 while their content is unchanged; a nested `observed_at` still counts, and other responses keep the tags they had before. On 304 keep the earlier body and its `observed_at`. After the server upgrade the first revalidation of such a response returns 200 with a new tag; on 0.9.0-rc.20 and earlier these tags change on every read. A 304 saves transfer and parsing, not the server's work: refresh a home-page row when the page opens or the user returns to it, not in a loop.

Missing technical data does not prove that a file is absent. `technical_status=unknown` requires an explicit player decision on trying an unverified original file. Known unsupported codecs remain a mismatch. The SDK's profile defaults to `allow_unverified=false`; applications must opt in deliberately.

Request additional details, tracks, subtitles and artwork when the page needs them. Never infer adult or hidden-library access from a media ID, another user's result, a cached page or a previously issued cursor. Each API call rechecks current authorization.
