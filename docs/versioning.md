# Version and compatibility

Kit version: **0.1.0-rc.2**. Build: **20261125.022**. Protocol: **SXAPI major 1**, base `/sxapi/v1`.

The minimum server source requirement is candidate **0.9.0-rc.9**. The specifications are bound to upstream commit `6629d3b777f4cd3624f6c42bd256cd89b978e0e9` (intended server version 0.9.0-rc.26) in [SOURCE.json](../spec/SOURCE.json). The full/client SHA256 values identify the exact synchronized bytes. No upstream release reference is supplied because this candidate is unpublished; compatibility remains NOT_VALIDATED. The bound commit itself passed the server API documentation checks. Source binding is not SDK CI or integration acceptance. This candidate depends on the new header-only video and subtitle contract, not the old URL-ticket transport. Do not advertise compatibility with RC8 or a historical server from a version string alone.

The RC26 specifications change only `info.version` (0.9.0-rc.25 to 0.9.0-rc.26): the player subset stays at 120 operations and the full specification at 389, and apart from that value both documents are byte-for-byte identical to RC25, with no operation, parameter, request or response field, status code, capability, limit or description added, removed or changed. This server version changes internal implementation only, with no HTTP interface change; clients need no change.

The RC25 specifications are additive over RC24: the player subset grows from 118 to 120 operations and the full specification from 387 to 389; apart from `info.version` the player subset changes 28 places, and the full specification changes 27 more in administration operations (library and user download settings, not published). The additions are the download permission and preload grants. `POST /prefetch/grants` asks before a preload, a whole-file cache or a download: the body `PrefetchGrantRequest` holds `media_id` (the work or the episode), `version_id` (a current file-backed version of it), `category` (`detail` for a detail-page or episode-page preload, `next_episode` for the next-episode preload, `cache` for a whole-file disk cache while playing, `download` for offline viewing) and `network` (`lan` or `wan`, recorded only), and allows no other members. Approval and refusal are both 200 (`PrefetchGrantDecision`, told apart by `granted`). An approval (`PrefetchGrantApproved`) carries `grant_id`, `max_bytes` (the bytes a `detail` or `next_episode` grant may read, 256 MiB by default, between 1 MiB and 10 GiB; null for `cache` and `download`, which are not counted), `max_seconds` (always null) and `expires_at` (the first stream read must start within 10 minutes of issue); a `download` approval adds the offline licence `license_expires_at` (30 days by default) and `renew_after` (half the licence). A refusal (`PrefetchGrantRefused`) carries `reason`: for `cache` and `download` the result of the three-tier download permission (site, library, user), `disabled_globally`, `not_opted_in`, `library_not_allowed` or `user_not_allowed`; for `detail` and `next_episode` `prefetch_disabled` (preloads are off) or `server_busy` (preload capacity is full); for any category `rate_limited` (at most 30 grants per user per minute); `server_busy` and `rate_limited` add `retry_after_seconds`. An invisible item or a version that is not a current file of it is 404 `not_found` and an invalid body 400; neither is a refusal. Send the request as an ordinary request, with no User-Agent purpose product and no `Sec-Purpose: prefetch`; a request marked as a preload meets the preload switch and slots first (403 `prefetch_disabled`, 429 `prefetch_busy`). `POST /prefetch/grants/{grant_id}/renew` renews the offline licence of the caller's `download` grant and decides the download permission again: a 200 approval with new `license_expires_at` and `renew_after` (same `grant_id` and `expires_at`) or a 200 refusal; another user's or an unknown grant, or an item no longer visible, is 404, and any other category is 409 `grant_not_renewable`. Without renewal the client stops offline playback of the copy when the licence ends and says why; the server deletes nothing remotely. `GET` and `HEAD` of `/playback/sessions/{id}/stream` and of disc file reads accept the optional header `STREAMIX-Grant: <grant_id>` (exactly one value); the grant must belong to the session's user and version: a present but invalid grant is 403 `grant_invalid` (never ordinary playback), and a first read after `expires_at` or after the offline licence is 403 `grant_expired`. A `detail` or `next_episode` read reserves what it serves from `max_bytes`: a Range longer than the remaining budget is cut to it and answered as a shorter 206 (trust `Content-Range`), a read without Range is served only when the whole file fits, and with nothing left the answer is 403 `grant_exhausted` without `Content-Range` (416 still means only a range outside the file); such reads take the preload lease outside the concurrent-stream limit whatever the User-Agent purpose, and return 403 `prefetch_disabled` once preloads are off. A `cache` or `download` read re-runs the download permission every time, answers a refusal with 403 and the reason as the error code, and is not counted. The User-Agent gains the purpose product `Streamix-Download/1` for whole-file disk caching and downloads (sent without `Sec-Purpose`); it is never a preload, and a read carrying it re-runs the download permission even without the grant header; when several purpose products appear the order is `Streamix-Play`, then `Streamix-Preload`, then `Streamix-Download`. Capabilities gain the required `features.download_permissions` (always true) and `features.prefetch_grants` (true when the server checks grants; false in Nimbus private mode until the private runtime checks them, when private stream reads check neither `STREAMIX-Grant` nor the download permission and `cache` or `download` is decided only at issue and renewal), plus the required `limits.prefetch_max_bytes_ceiling` (10737418240, 10 GiB); the new schemas are `PrefetchGrantRequest`, `PrefetchGrantDecision`, `PrefetchGrantApproved` and `PrefetchGrantRefused`. Normal playback, its buffering and a cache of only the watched parts need no grant. Check `features.prefetch_grants` first: an RC24 or earlier server has neither capability nor operation, so keep the earlier preload rules there. See [preload grants and downloads](downloads.md).

The RC24 specifications are additive over RC23: the player subset stays at 118 operations and the full specification at 387, with no operation or parameter added or removed; apart from `info.version` both documents change the same nine places. A new schema `VersionDisplay` is added, and `Version` and `BestVersion` gain `display`, a required, nullable server-built short version name. For a version the server records as adult origin, the name is built from the code in the file name (normalized, for example `ABCD-123`), its tags (Chinese or English subtitles, uncensored, leak, decensored, AI decensored, VR, 4K/8K, frame rate, HDR, part CDn) and the technical differences that tell it apart from the other versions of the same work and episode; without a code it falls back to a short title taken from the file name, then the technical facts, then `版本 N` (version N), and it is never the whole file name. `display.text` is the name to show, already unique among the versions of the same work and episode, at most 40 characters and 40 columns (an East Asian character counts two); `basis` says where it came from (`code`, `title`, `technical` or `ordinal`); `code` and `family` hold the normalized code and its family only when `basis` is `code`; `tags` lists the machine names of the tags in `text` in display order (for example `zh_sub`, `uncensored`, `leak`, `4k`, `cd<N>`); `rules_version` names the rules file that produced the name (`YYYY.MM.patch`). Ordinary versions return null and keep their client-built labels. Adult works now list their versions in the adult order: Chinese subtitles first, then leak > uncensored > decensored > AI decensored, then resolution, then bitrate (the weights live in the server's versioned rules file); the parts of one variant stay together in part order and an episode group keeps the place of its first entry; pages of an adult work are cut from that order (the cursor carries the position), and a work with more than 2000 versions keeps the quality order. `best_version` is the first entry of the adult order, and `BestVersion.display` is that version's `Version.display`. Capabilities gain the required `features.version_display` (always true from RC24). With it, show `display.text` instead of building a name; a server at 0.9.0-rc.23 or earlier has neither the capability nor the member and keeps the quality order. `BestVersion` allows no other members, so a client that strictly validates against the RC23 or an earlier specification rejects RC24 responses and must update; conversely, responses from an older server have no `display`.

The RC23 specifications change descriptions only: the player subset stays at 118 operations and the full specification at 387, with no operation, parameter, request or response field, status code, capability or limit added or removed; 50 descriptions and `info.version` changed. The changed descriptions record three server behaviors. Preparing playback (`POST /playback/sessions`): when the final recheck or the ticket fails after the session is stored (for example a refused private issuance), the server ends that session before returning the error, so it does not count toward the 32 active prepared sessions per user. Folder discs in Nimbus private mode: preparing with the `version_id` of a folder disc returns 409 `disc_folder` before any session is written or private ticket issued (the private runtime serves one file per session), and renewing the ticket of a session bound to a folder disc (`POST /playback/sessions/{id}/tickets`) returns 409 `disc_folder` without issuing a private ticket; both 409 descriptions now name `disc_folder`. Image discs and ordinary files are unchanged. Preload exemption: `features.prefetch_stream_limit_exempt` and the stream and disc-file read descriptions now say that in Nimbus private mode a preload stays outside the concurrent-stream limit only when the composed private runtime declares it; otherwise the private host keeps one lease for preload and playback, as it always did in private mode through RC22. The other descriptions only replace internal database names (tables, columns, indexes, migration numbers) with public wording and keep their meaning. Clients need no code change: keep treating a failed prepare as an error, and in private mode rely on `prefetch_stream_limit_exempt` from `/capabilities`.

The RC22 specifications are additive over RC21: the player subset grows from 117 to 118 operations and the full specification from 386 to 387. Two lookups by external ID let a page that lists people or works by TMDB or IMDb ID (a chart, a filmography) mark and open the ones this server has. `GET /persons?external_ids=` looks persons up by 1 to 50 comma-separated items (at most 2048 bytes in all), each `tmdb:<TMDB person number>` or `imdb:nm<digits>` (ignoring case and surrounding whitespace; anything else is 400); only `library_id` may join it, and `q`, `limit`, `cursor` or `include_total` with it are 400. Without `external_ids` it is the person search as before. The answer is a `PersonLookupPage` (only `data`, no `total` or `next_cursor`): each person has the search fields (`id`, `name`, `known_for_department`, `image`, `external_ids`) plus `media_count` (the works the account can see that credit the person, equal to the `total` of `GET /persons/{id}/media` with the same `library_id` at the same moment), `movie_count`, `series_count` and `matched` (the requested items that name the person, as sent, in request order, each once). A person without a visible work and an unknown ID have no row; rows follow the first requested item that names them. `POST /media/lookup` takes `{"ids": [...], "library_id": ...}` with 1 to 500 IDs of 1 to 64 bytes: a typed TMDB ID `tmdb:movie:<n>` or `tmdb:tv:<n>` (at most one work), or a `GET /media` `external_ids` item: `tmdb:<n>` (the movie and the series with that number, one row each), `imdb:tt<digits>` or `tvdb:<digits>`. Only matches are returned: one `{id, media_id, media_type, version_count}` row per requested ID and visible work, the ID echoed as sent, in request order, plus `observed_at`; an ID's rows are exactly the works `GET /media?external_ids=<that ID>` lists at the same moment (with `media_type` for a typed TMDB ID). Open a work with `GET /media/{media_id}`. The body is at most 131072 bytes; unknown fields, a malformed body, a missing or non-JSON Content-Type, or a query string are 400, and a hidden `library_id` is 404. The operation only reads; it is a POST because 500 IDs do not fit in a URL. `GET /media/ids` rows (`MediaStamp`) and `GET /persons/{id}/media` entries (`RelationshipPersonMedia`) add the required field `external_ids`, the work's `Media.external_ids` (a `{tmdb, imdb, tvdb}` object on an ordinary film or series with IDs, otherwise null), so a client maps external IDs to works without fetching each one. Capabilities add `features.person_lookup_by_external_id` and `features.media_lookup_batch`, plus `limits.person_external_ids_max` (50) and `limits.media_lookup_ids_max` (500); new schemas `PersonLookupPage`, `PersonLookupItem`, `MediaLookupRequest`, `MediaLookup` and `MediaLookupRow`. Check the matching capability before using either lookup: an RC21 or earlier server has neither operation and no `external_ids` in those two lists; without `media_lookup_batch`, fall back to `GET /media?external_ids=` with at most `limits.media_external_ids_max` (50) IDs per request.

The RC21 specifications add and remove no operations: the player subset stays at 117 operations and the full specification at 386. Only the `ETag` header description of the 63 tagged JSON reads changed (on their 200 and 304 responses); there are no new parameters, response fields or capabilities. For a JSON object response with a top-level `observed_at` (the read time), the `ETag` no longer covers `observed_at`: when personal lists such as `/users/me/resume`, `/users/me/next-up` and `/users/me/favorites`, facet pages and similar reads are unchanged, sending the previous `ETag` in `If-None-Match` returns 304 although `observed_at` differs on every read. A nested `observed_at` still counts, and every other response keeps exactly the tag it had before. On 304 keep the earlier body and its `observed_at`. A 304 saves transfer and client parsing; the server still runs the read. Clients need no code change and benefit as long as they send the `ETag` back; an RC20 or earlier server changes these tags on every read.

The RC20 specifications add and remove no operations: the player subset stays at 117 operations and the full specification at 386. `GET /media/facets/{kind}` now serves whole answers: the answer for one account's visible inventory, facet kind, `media_type` and genre-name language is computed once and kept in the server for at most 600 seconds (`capabilities.limits.media_facet_max_age_seconds`); pages, `q` and cursors are cut from it with the same rules, so they match a fresh computation. Authorization is checked on every request, and a change of account, library grants or library definitions never reuses an earlier answer; only content changes (new or removed files, metadata, tracks) may appear up to 600 seconds late, and `observed_at` is when the served answer was computed, at most that long before the request. Answers used in the last 30 minutes are recomputed in the background after 7 minutes, so regular browsing is served from memory. Capabilities add `features.media_facet_cache` and `limits.media_facet_max_age_seconds`; there are no new parameters or response fields, and clients need no change.

The RC19 specifications are additive over RC18: the player subset grows from 116 to 117 operations and the full specification from 385 to 386. New `POST /media/studio-counts` counts the visible works of production company or network names in one request, for a page with one row per platform, network or studio that hides the empty rows. The JSON body takes only `names` (up to 200 names, each counted on its own), `groups` (up to 200 groups, each with an `id` of 1 to 64 bytes and 1 to 20 `names`; put the spellings of one brand in a group, and a work counts once per group), `library_id` and `media_type`; at least one name, at most 1000 in all, and at most 524288 bytes. The response has `data` (one row per name) and `groups` (one row per group), both in request order with names and IDs echoed as sent, each row with `media_count`, `movie_count` and `series_count`, plus `observed_at` and `catalog_only`. A name row equals the total of `GET /media?studios=<that name>` and a group row the total of `GET /media?studios=<all its names>`, with the same `library_id`, `media_type` and authorization rules. Unknown fields, a malformed body, a missing or non-JSON Content-Type, or a query string are 400. It returns counts only; open a row with `GET /media?studios=<the same names>`. The `studios` filter of `GET /media`, `GET /media/initials` and `GET /media/ids` now takes escapes: write a comma inside a name as `\,` and a backslash as `\\`; any other backslash is literal (for example `Daylight Entertainment Co.\, Ltd.`), so a name with a comma no longer needs `studio_ids`. Capabilities add `features.media_studio_counts`; new schemas `StudioCountsRequest`, `StudioCountsGroup`, `StudioCount`, `StudioCountsGroupResult` and `StudioCounts`; no new limits. An RC18 or earlier server does not advertise it; fall back to one `GET /media?studios=<names>&limit=1` per row.

The RC18 specifications are additive over RC17: the player subset stays at 116 operations and the full specification at 385. `GET /media`, `GET /media/initials` and `GET /media/ids` add two filters: `studios` (production company or network names, comma-separated, whole names ignoring case, no substring or wildcard) and `studio_ids` (TMDB company or network numbers, comma-separated), each 1 to 20 values; a work matches when it has any value of a parameter, and the parameters combine with `studio_id` and every other filter, work with every sort and keep earlier cursors valid. A work's studios are `Media.studios`: production companies for a film, production companies and then networks for a series, so a platform such as Netflix, HBO or iQIYI is filtered as a studio and there is no separate network filter. Before usage require runtime capabilities `playback_ticket_header=true`, `credentials_in_urls=false` and the needed individual features. The server also declares the additive aliases `stream_ticket_header=true` and `stream_query_ticket=false`; these do not enable a URL transport or change the SDK checks. Missing capability keys are unsupported. No lenient legacy fallback is provided. A deployment can disable features even when the protocol/schema is present.

Kit uses its own SemVer. Pre-release server integrations use a pre-release Kit until formally accepted; a final server release does not automatically finalize this Kit. Breaking SXAPI changes require a new protocol major path and a corresponding Kit major. Compatible additive fields may be retained as unknown fields by typed response models.

`sync_spec.py` records the full upstream commit, release, minimum server version, synchronized timestamp and SHA256 of the exact full and player-subset bytes.
